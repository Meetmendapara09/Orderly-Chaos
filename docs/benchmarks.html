Reading these numbers

Realistic books have hundreds to a few thousand active levels, so most operations behave like limit_existing_levels and mixed_flow. limit_new_levels deliberately builds a book with a million distinct prices, far beyond any real instrument, to show the cost when every access misses the CPU cache.

Worst-case fix in v0.2.0

Before v0.2.0, price levels were kept in an unbalanced binary tree. When prices arrive in rising or falling order (a trending market), such a tree degenerates into a linked list and every new level costs O(L). v0.2.0 uses a balanced tree, which guarantees O(log L). Same benchmark, same machine, strictly increasing prices:

Price levelsv0.1 (unbalanced)v0.2 (balanced)Speed-up
10,00019,535 ns/op365 ns/op53x
50,00087,798 ns/op414 ns/op212x
100,000178,952 ns/op400 ns/op447x

For random prices and for orders joining existing levels the two versions perform the same within measurement noise, so the fix costs nothing in the common case. The test suite includes a 200,000-level monotonic scenario that takes tens of seconds with the old tree and completes in well under a second.

Methodology

  • Each scenario prepares its book outside the timed region, then times only the operations.
  • Every scenario runs 7 times on a fresh book; the median is reported to reject outliers.
  • All order IDs are unique and all inputs are valid, so no time is spent on rejections.
  • Results feed a volatile sink so the compiler cannot remove the work.
  • Trade handlers are not installed; with a handler, each trade adds the cost of your callback.

Source: benchmarks/benchmark_lob.cpp.

Reproduce

make bench                                              # all scenarios
bazel run -c opt //benchmarks:benchmark_lob -- --quick  # smaller n, faster
bazel run -c opt //benchmarks:benchmark_lob -- cancel   # scenarios matching "cancel"
bazel run -c opt //examples/cpp:market_simulation -- 1000000
Always benchmark optimized builds

Bazel's default fastbuild mode disables optimization and is many times slower. Use -c opt, close other workloads, and run on a machine with a stable CPU frequency for repeatable results.

Python overhead

Each Python call crosses into the native library through ctypes and validates its arguments. On the machine above a query such as best_buy() costs about 1.4 microseconds and a limit() call about 5 microseconds, so a Python program processes roughly 200,000 orders per second. That is plenty for replays, research, and simulations; for the highest throughput drive the book from C++ and use Python for orchestration and analysis.

Performance tips

  • Use one book per instrument and one thread per book; books never share state.
  • Choose the tick size of the instrument as the price unit, so prices are small, dense integers.
  • Install a trade handler only when you need trade events; without one, no trade objects are created.
  • Prefer reduce over cancel-and-replace when lowering an order's size: it is cheaper and keeps queue priority.
  • Use depth(side, n) with a small n for snapshots; its cost is proportional to the levels returned.
