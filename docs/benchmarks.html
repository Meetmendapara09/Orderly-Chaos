Benchmarking Methodology

Benchmarks measure the real C++ engine — not the Python wrapper — compiled with production flags (-O2 -march=native -pipe -pedantic -Wall). The same binary you build with bazel build //orderly_chaos:copy_dll is what gets timed. Results below are representative on a modern x86-64 desktop; your numbers will vary slightly with CPU and OS, but the relative ordering stays the same.

Run the suite yourself (requires the prerequisites from Getting Started):

# One command — prints a latency table to your terminal
bazel test //benchmark:benchmark_lob_test --test_output=streamed

# Run everything (unit tests + benchmarks) to confirm no regressions
bazel test //... --test_output=errors

How to read the tables: Time is wall-clock latency per operation, Throughput is operations per second at that latency, and Complexity tells you how the cost grows as the book gets deeper. n = number of distinct price levels, k = number of levels a single order walks through while matching.

Limit Order Performance

A limit order either rests in the book or crosses the spread and matches immediately. The common case — adding at an existing price level — is a single queue append (O(1)). Creating a new price level inserts one node into the red-black tree (O(log n)). Because most orders land on existing levels in a liquid book, average cost stays near 0.3µs.

OperationOrdersTimeThroughputComplexity
Insert single limit order1~0.3µs~3.3M/secO(log n) worst · O(1) at existing price
Insert 100 limit orders100~30µs~3.3M/secO(log n)
Insert 1,000 limit orders1K~300µs~3.3M/secO(log n)
Insert 10,000 limit orders10K~3ms~3.3M/secO(log n)

Throughput holds steady as you scale — the tree grows by price levels, not by orders, so 10K orders across 20 levels is barely slower per order than 100.

Market Order (Matching) Performance

A market order walks the opposite side level by level, filling FIFO queues inside each level. One exhausted price level is one O(log n) tree removal — so matching k levels costs O(k log n). In practice, most market orders touch 1–3 levels, so sub-microsecond latency is the norm; sweeping a deep book (100 levels) is still under 30µs.

OperationMatchesTimeThroughputComplexity
Market buy (cross 1 level)1 level~0.5µs~2.0M/secO(log n)
Market sell (cross 5 levels)5 levels~1.2µs~833K/secO(k log n)
Market buy (cross 10 levels)10 levels~2.5µs~400K/secO(k log n)
Market sell (cross 100 levels)100 levels~25µs~40K/secO(k log n)

k = number of price levels touched, n = distinct price levels in the book. A single-level market order is just one tree removal plus queue drains — hence ~0.5µs.

Full Complexity Analysis

Every operation's cost follows from the structure it touches. The book keeps best price, total volume, and order count as incremental counters — reads never walk the tree. The tree is only touched when a new price level appears or the last order at a level is removed. This is why best_sell(), best_buy(), volume(), and count() are all O(1).

Memory Efficiency

The book allocates one Limit node per price level and one Order node per live order — nothing else scales with book depth. Aggregates (best pointer, volume, count) are a fixed 24 bytes per side and updated incrementally, never recomputed.

  • Price level (tree node): ~64 bytes — one per distinct price. A book with 50 price levels uses ~3.2KB of tree overhead.
  • Order node: ~40 bytes — one per live order. 10,000 resting orders ≈ 390KB + hash map buckets.
  • Order lookup: tsl::robin_map hash map, amortized O(1), O(n) space for n orders.
  • Cached aggregates: O(1) extra per LimitTree — best pointer, volume, count, last_best_price.
  • No per-match allocation: matching walks existing nodes and unlinks them; no new heap work on the hot path.

Example: 10,000 orders across 20 price levels ≈ 400KB orders + 1.3KB levels + hash buckets — comfortably fits in L2 cache.

Run Your Own Benchmarks

To reproduce the numbers above on your machine — or to measure a change you made to the engine — use the same command CI uses: 

# Full suite with streamed output (latency table + PASS/FAIL)
bazel test //benchmark:benchmark_lob_test --test_output=streamed

# If you touched the engine, also confirm correctness first
bazel test //test:all --test_output=errors   # 3/3 suites should PASS

For a quick sanity check without Bazel, build the example binary and time it: 

bazel build //main:dummy_matching -c opt
./bazel-bin/main/dummy_matching  # simulates 10M orders, prints elapsed ms
