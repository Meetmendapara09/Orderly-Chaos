System Architecture

No trading background needed. This page explains how a price-time priority order book works, how Orderly Chaos implements it in three simple layers (C++ core → C API → Python), and why the hot path stays fast with O(1) best-price reads and incremental volume tracking.

Mental Model — What Is an Order Book?

An order book is two sorted lists — bids (people who want to buy) and asks (people who want to sell) — each grouped by price, with orders inside each price level queued in the order they arrived. When a new order's price crosses the best price on the opposite side, a trade happens immediately (price priority first, then time priority). Otherwise the order rests in the book until someone matches it or it is cancelled.

Example: best ask is $102.50, best bid is $102.40. A new buy at $102.50 crosses the spread and matches the ask — the earliest order at $102.50 is filled first (time priority).

Layer 1: C++ Core — where speed lives

include/limit_order_book.hpp holds the complete matching logic. It owns two LimitTree instances (one for buys, one for sells) and a hash map from order ID to order. All hot-path methods are inline so the compiler can eliminate call overhead. This layer is header-only — C++ users just add include/ to their include path.

Read the source: limit_order_book.hpp:43 (book), limit_tree.hpp:157 (one side), structures.hpp:57 (price levels and orders).

Layer 2: C API — the stable bridge

include/lib_lob.hpp exposes the same operations as extern "C" functions (new_(), limit_sell(), best_sell(), delete_(), …). Because the ABI is plain C, any language that can call C can use the engine without rewriting it — Python, Rust, Go, Java, C#. The functions are thin wrappers — they forward directly to the C++ methods with no extra allocation or copying.

Layer 3: Python ctypes — no compiled extension

orderly_chaos/library.py loads lib_orderly_chaos.dll (or .so on Linux/macOS) with ctypes.CDLL and declares each function's prototype through argtypes/restype, which gives type-checked, documented calls instead of raw pointer soup. orderly_chaos/orderly_chaos.py then wraps those raw calls in a Pythonic LimitOrderBook class. No Cython, no pybind11, no compiler needed on the Python side after the DLL is built — and the GIL is released during each call, so the engine runs at native speed inside a multi-threaded host.

Data Structures — Why It Is Fast

Every operation's cost comes from the data structure it touches. The book is designed so the most common queries — best price, total volume, order count — never touch the tree at all.

LimitTree — a red-black tree with cached aggregates

Each side of the book (buy/sell) is a LimitTree (limit_tree.hpp:157). Underneath is a red-black tree (self-balancing BST — guaranteed O(log n) insert/remove, no degenerate paths) from vendor/binary-search-tree, keyed by price. The tree is augmented with three cached values that are updated incrementally on every insert/remove, so reads are constant time:

  • Best pointer (LimitTree::best) — always points to the best price level (highest bid / lowest ask). best_sell() / best_buy() just dereference it: O(1). No tree walk.
  • Volume accumulator (LimitTree::volume) — total shares on this side. Maintained as volume += quantity on insert and volume -= quantity on cancel/match. volume() returns it directly: O(1).
  • Count accumulator (LimitTree::count) — number of orders on this side. Same incremental update: O(1).
  • Last best price (last_best_price) — previous best before the latest mutation, used to detect price moves without re-querying.

The tree itself is only touched when a new price level appears or the last order at a price is removed — both are O(log n) where n is the number of distinct price levels (typically far smaller than the number of orders). Adding a second order at an existing price is O(1) — it just appends to that level's queue.

Order Store — hash map for O(1) cancel and lookup

std::unordered_map<UID, Order> orders in limit_order_book.hpp:50 maps every live order ID to its order object. Cancellation and lookup by ID never scan the tree — they hash directly to the order in O(1) average time, then follow the order's limit pointer to its price level.

Doubly-Linked List — FIFO queue at each price

At each price level, orders sit in a doubly-linked list (vendor/doubly-linked-list) in arrival order. Insertion appends to the tail, removal unlinks the node — both O(1). The head of the best level's list is always the next order to match, which is how time priority is enforced without sorting.

Complexity at a glance
best_sell / best_buy / volume / count / has → O(1) (cached).
limit_sell / limit_buy at new price → O(log n) (tree insert).
limit at existing price → O(1) (queue append).
cancel / reduce → O(1) hash lookup + O(log n) only if last order at that price.
market crossing k levels → O(k log n) (one tree removal per exhausted level).

Matching Algorithm — Price-Time Priority

Every trade follows two rules, in order:

  1. Price priority — the best price on the opposite side is matched first (highest bid for a sell, lowest ask for a buy).
  2. Time priority — among orders at the same price, the earliest order is matched first (FIFO queue).

Build System — Bazel with Bzlmod

The project uses Bazel 7+ with Bzlmod (the new module system, default since Bazel 7). Dependencies are declared in MODULE.bazel and fetched automatically on first build (or pre-fetched with bazel fetch //...) — no manual git submodule or vendoring for Google Test. The archive is pinned by SHA-256 in an http_archive, so every machine builds from bit-identical sources. 

bazel test //test:all                          # C++ unit tests (Google Test)
bazel test //benchmark:benchmark_lob_test      # performance benchmarks
bazel build //orderly_chaos:copy_dll           # shared library + copy next to Python package
bazel build //main:dummy_matching              # example binary (10M orders)
bazel test //...                               # everything

Key files:

  • MODULE.bazel — module name, rules_cc + platforms, and http_archive for Google Test (fetched from GitHub, built via patches/googletest.BUILD).
  • BUILD.bazel in each package (test/, benchmark/, orderly_chaos/, …) — defines cc_test / cc_binary targets.
  • toolchain/BUILD.bazel — custom MinGW-w64 toolchain for Windows (Strawberry Perl). Edit STRAWBERRY_BIN there if your g++.exe lives elsewhere.
  • .bazelrc — -std=c++17 -O2, static MinGW linking, and the BAZEL_SH host config.
